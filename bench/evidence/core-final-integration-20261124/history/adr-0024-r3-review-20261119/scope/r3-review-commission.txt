## 四、R2-01：原子文件发布与并发安全

Priority: P2, data integrity.

Inspect:

- `internal/editing/engine.go`
- `internal/editing/fileid_unix.go`
- `internal/editing/fileid_windows.go`
- `internal/editing/publish_darwin.go`
- `internal/editing/publish_linux.go`
- `internal/editing/publish_other_unix.go`
- `internal/toolset/editing.go`

Carbon's new design:

1. Create a private sibling temporary file.
2. Write and validate content in the temporary file.
3. Publish to the destination using atomic no-replace semantics.
4. Never overwrite an existing destination.
5. Clean up only temporary files owned by the current operation.
6. Preserve external files on conflict.

### A. Unix publication

Independently verify:

- Darwin `os.Link` and `RenameatxNp(RENAME_EXCL)`.
- Linux `Renameat2(RENAME_NOREPLACE)`.
- Filesystem support and error handling.
- Same-directory guarantees.
- Cross-device behavior.
- Directory synchronization and durability assumptions.
- Symlink handling.
- Permission preservation.
- Temporary file cleanup.

Do not assume all Unix filesystems provide identical semantics.

### B. Windows publication

Inspect the actual `MoveFileExW` flags and error handling.

Verify:

- Existing destination is never replaced.
- Concurrent creation is rejected.
- Reparse points and symlinks are handled safely.
- File handles are closed at the correct time.
- Temporary files are cleaned without deleting external files.
- Unsupported filesystem behavior is handled conservatively.

Windows cross-compilation is not native runtime verification.

### C. Race and failure scenarios

Test or independently reproduce:

1. Two processes publish the same destination.
2. Destination exists before publication.
3. Destination is created during publication.
4. Temporary file write fails.
5. Publication fails.
6. Destination is replaced externally.
7. Symlink destination.
8. Permission denied.
9. Directory removed during publication.
10. Disk or filesystem error.
11. Process termination before publication.
12. Process termination after publication.

Verify the original external file remains byte-for-byte intact.

### D. Final verdict for R2-01

Determine whether the implementation genuinely guarantees:

**An operation may never delete or overwrite a file that it did not atomically publish as its own destination.**

Identify any filesystem-specific limitations.

## 五、R2-02：Gate State 与滚动修复历史

Priority: P2, long-run reliability.

Inspect:

- `internal/agent/policy.go`
- `internal/agent/transcript.go`
- `internal/agent/send.go`
- `internal/agent/loop.go`
- `internal/session/executions.go`
- `internal/session/store.go`

New design:

- Persistent GateFeedback.
- Repair Stage R1 / R2 / R3.
- PostBlockCausalFloorSeq.
- Up to eight body-free CausalEvidenceRef entries.
- Rolling history strictly after BlockSeq.
- Pinned Gate State and rolling Messages must not duplicate or lose evidence.

### A. State lifecycle

Verify:

1. GateFeedback survives ordinary transcript sliding.
2. GateFeedback survives process termination.
3. Repair Stage advances monotonically.
4. PostBlockCausalFloorSeq is derived from valid evidence.
5. CausalEvidenceRef points to real persisted evidence.
6. Unknown evidence cannot be promoted to Proven.
7. Proven evidence only replaces history when the replacement relationship is actually valid.
8. The eight-reference limit does not silently discard necessary evidence.
9. New user input resets or closes the old repair cycle correctly.
10. Multiple gate failures do not mix independent repair cycles.

### B. Rolling history

Verify:

- Only eligible post-block history can slide.
- Latest atomic message groups remain complete.
- Tool calls and tool results remain paired.
- Required gate feedback remains available.
- Unresolved evidence is not discarded.
- State and Messages do not duplicate the same content.
- Compact and Full projections preserve the same repair semantics.

Use a real SQLite database.

Compare:

- Continuous execution.
- Process termination and cold Resume.
- Resume after R1.
- Resume after R2.
- Resume after R3.
- Resume after a Proven modification.
- Resume after an Unknown modification.
- Resume after multiple GateBlocked events.

Compare the complete state, not just MinRequiredSeq:

- GateFeedback.
- Repair Stage.
- Original BlockSeq.
- PostBlockCausalFloorSeq.
- CausalEvidenceRef.
- MutationEvidence.
- Current rolling history start.
- Actual projected messages.
- ReplayDecision.

The same persisted history must produce the same repair state after Resume.
