# LumenCortex 实现原则

本文说明如何把架构决定落实为可靠的 Go 代码。它是开发约束，不代表所有规划能力都已完成。

## 1. 只保留一套生产 Runtime 和一个权威来源

Go 是唯一正式生产 Runtime。Agent 执行、Session 存储、权限和生命周期必须有唯一权威实现。模块可以分工，但不能各自维护互相冲突的事实。历史 Node.js 代码只作参考。

**原因：** 两套 Runtime 或重复 Registry 会产生权限、状态、恢复和行为差异。

## 2. 分开提议、授权、执行和证据

模型可以提出操作或判断，但不能自己批准操作、宣称工具成功，也不能把自己的文字变成验证证据。

1. 模型提出建议。
2. Core 检查身份、范围、权限和当前状态。
3. Host 执行获准的操作。
4. Core 保存真实结果和来源。
5. 验证器只检查自己负责证明的内容。
6. Core 提交状态变化。

**原因：** 模型输出是不可信输入；权限和持久化事实必须由确定性代码和真实观察结果控制。

## 3. 明确每份数据的归属

每个可持久化或可修改对象都必须明确 Owner 和读写者，例如 Session、Run、Worker、任务、工作区、Artifact、知识或经验。跨 Session 共享必须显式记录来源。一个使用者的反馈不能泄漏给另一个使用者；来源撤销后，依赖它的内容必须失效；删除一个使用者的数据不能误删其他人的数据。

**原因：** 隐式共享会导致隐私泄漏、租约丢失和跨 Session 数据污染。

## 4. 写入时检查版本

并发状态必须使用 expected revision、CAS、Lease 或事务。发生冲突后先重新读取。不能用旧快照覆盖新内容。所有文件写入，包括 Eval Artifact 导出、AST 编辑和 LSP 编辑，都必须经过统一 Editing Engine 的保护路径。

**原因：** 读到某个版本，不代表之后仍有权覆盖它。

## 5. 所有资源都必须有上限

模型上下文、工具输出、Agent 并发、子任务、后台 Job、进程时长、内存、CPU、事件队列、Artifact 大小和历史保留都必须有明确限制，并在创建资源前执行。

**原因：** 长时间任务不能导致内存、进程数量或成本无限增长。

## 6. 取消和清理属于正确性

取消必须传递到当前 Provider 请求、工具、子 Run 和受管理进程。清理完成后才能发布终态。如果外部操作结果无法确认，记录 outcome_unknown，不能猜测成功，也不能盲目重试非幂等操作。

**原因：** 停止调用方，不代表它启动的工作已经停止。

## 7. 持久化事实，不持久化无限增长的运行时状态

长期历史保存在 SQLite 或明确的 Artifact Store。内存只保存当前操作需要的有界数据。事件只是观察记录，不是权限或完成证明。可重建索引不能成为第二个权威数据源。

**原因：** 进程重启后应恢复已提交事实，但不能假装进程和内存堆也恢复了。

## 8. 把路径、项目和外部输入视为不可信

规范化工作区身份；逐段检查路径和符号链接；项目配置必须经过明确的工作区信任检查；密钥只通过运行时引用读取，不能写入日志或模型上下文。

**原因：** 仓库内容和工具参数由外部提供，不能当成可信策略。

## 9. 缺少权限或证据时拒绝执行

如果无法确认范围、来源、身份、权限、资源隔离或验证结果，就拒绝操作或明确返回 Unknown。不能静默降低安全要求，也不能把证据缺失当作成功。

**原因：** 明确拒绝比无法证明的状态变更安全。

## 10. 测试必须对应真实契约

回归测试应能在旧实现或故意错误的实现上失败，在修复后通过。尽可能测试真实公开调用路径。PASS、FAIL、SKIP 分开统计，并记录 OS、架构、Commit 和命令。交叉编译不等于原生运行验证。

**原因：** 测试只能证明它实际覆盖的行为。

## 11. 分开写架构目标和当前实现

每项能力必须标记为 main 已实现、部分实现、仅候选分支、计划中或证据不足。架构图、Node 参考实现、本地分支和孤立测试都不能证明 Go 正式版本已经交付。

**原因：** 文档必须与用户实际能运行的版本一致。

## 12. Cognitive Core 专项原则

- 保留原始任务经历和证据；摘要只能作为派生视图。
- 区分工作记忆、情景记忆、语义记忆和程序性记忆。
- 最近使用、使用频率、实际价值、模型置信度和证据强度不是同一个指标。
- 只有当前任务满足经验前提时才允许复用。
- 模型生成的经验只是候选，验证后才能按限定范围采纳。
- 未知、冲突和过期状态必须明确保留。
- 不能把存储、检索或总结直接称为学习。

## 13. 文档也是交付的一部分

行为变化后，同步更新权威组件文档、中文版、验证证据和已知限制。README 保持简洁。ADR 记录长期决策，Report 记录某次实施或审查过程。

## 代码审核清单

- 这份状态由谁拥有？谁可以读取和修改？
- 如何证明操作已获授权？
- 进程在每个边界崩溃会发生什么？
- 旧版本能否覆盖新状态？
- 资源限制是否在启动前执行？
- 操作能否取消并完成清理？
- 哪份证据能证明当前结论？
- 功能在 Go main，还是只在候选分支？
- 英文和中文文档是否一起更新？
