## 2. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | The deletion is a state machine on `source_fences` rows with `scope_kind = 'privacy'`: `BeginPrivacyDeletion` commits, in one write transaction, the revocation of the root (same reach as `RevokeSession`, via the extracted `revokeIn`) and one `cleanup_pending` privacy row per deleted id; the root's row carries `{root, ids, epoch}` and the cleanup cursor. | No new table (G-1 table budget); the fence is committed before any content is touched, so from then on no run, read or edge uses it. |
| D2 | `PurgeStep` = one bounded batch (`PurgeBatchRows`) in one `BEGIN IMMEDIATE` with `secure_delete = ON`, in order: the deleted sessions' rows table by table; the copies in other sessions' transcripts (tool results / task results naming a deleted id, rewritten without content, cursor `$.scan`); parent checkpoints reduced to the id/status whitelist; journal rows reduced to the whitelist (cursor in `metadata`); the session rows. | Short write transactions; every step re-reads its position from the database, so an interrupted step is re-run, never skipped. |
| D3 | **After the rows, a rebuild (`VACUUM`) is owed before the fences become `cleaned`** (`$.rebuild` on the root's privacy row). | Found during this slice: with `secure_delete` alone the byte scan still found the sentinel in the **main file** (an `agent_steps` cell on page 9). Earlier page splits/defragmentation, done with `secure_delete` off by every ordinary write, leave older copies in unallocated space that the deletion never touches — the same mechanism `internal/migrate` already handles with `markerVacuum`. Only a rebuild removes them. Mutation N1 below shows the scan fails without it. |
| D4 | `VACUUM` runs in-process on the Store's own pinned connection under the shared `db.lock`, outside any transaction the step opened, not through the migrate exclusive path. | The exclusive path would make every other process's Open wait/fail (`ErrDatabaseInUse`) while a marker is pending. In WAL mode other processes' readers are not blocked; a concurrent writer waits up to `busy_timeout` or fails busy, and the deletion then stays `cleanup_pending` for the next attempt. Cost: one copy of the database per deletion (user-initiated, rare). |
| D5 | WAL: `OweCheckpoint` writes the existing durable `checkpoint.pending` marker before the first batch. After the rebuild the root's privacy row owes the truncation (`$.settle`); the step runs `wal_checkpoint(TRUNCATE)` (bounded by `migrate.CheckpointWait`) and **only a complete truncation turns the fences `cleaned`**. A blocked truncation returns `session.ErrCleanupPending` (`runtime.ErrDeletionPending`): `DeleteSession` fails, the deletion stays `cleanup_pending`, the marker stays; the next `DeleteSession`/`Open` retries. A marker that owes a migrate rebuild is left alone (the deletion stays pending until the next Open's exclusive path). | Reuses the migrate marker and the existing privacy row cursor (`$.scan`/`$.rebuild`/`$.settle`); no new table or state value. Changed in §9. |
| D6 | Resume: `Engine.Open` (`resumeDeletions`) and the next `DeleteSession` of the root finish a pending deletion. `DeleteSession` checks for a pending deletion **before** taking the root's run lock, because after the row batch the root row is gone while the rebuild is still owed. | Plan failure path "SIGKILL between batches: resume cleanup, not consumption". |
| D7 | Plan line "`cleanup_pending` 期间调用删除 API：返回错误" is implemented as: a `DeleteSession` while another caller holds one of the deleted sessions' run locks returns `ErrRunHeld`, and while a reader blocks the WAL truncation `ErrDeletionPending`; the deletion stays pending either way; a retry after an interruption resumes it. | Returning an error to every retry would leave a crash-interrupted deletion unfinishable until restart, while Open resumes it anyway. Consistent with O-3 (§8). |
| D8 | A session that is running is not cancelled by `DeleteSession`; it fails `ErrRunHeld` as before (ADR-0005). Readers of the deleted session in other sessions are fenced and their runs cancelled through the revocation (T3-S1). | The deleted session's own late output cannot land: its run lock is held by the deletion. |
| D9 | Journal rows without `sessionId` (pre-whitelist rows, e.g. `tool.shell` commands) are **all** reduced to the whitelist on the first deletion, not only rows naming a deleted id. | Such rows cannot be attributed and can hold any content. Approved by O-3 (§8). |
| D10 | The fences stay after `cleaned`: `SessionWithdrawn(id)` stays true, a later edge citing the id is refused, other sessions' edges citing it resolve to `source_missing`. An explicit re-import (`ImportSessions`) of the same source id is refused while that id's deletion is `cleanup_pending` (`ErrCleanupPending`); after it finished, the re-import removes the `session` fences that deletion committed on the id and **keeps the `privacy` row** as the body-free record of the deletion. | Re-import is a new user decision bringing content from outside the database. Changed in §9: the earlier code deleted the privacy row and left the withdrawing session fence (state `active`, never `cleaned`), so a re-imported session stayed withdrawn and the record was lost. |
| D11 | Digests computed from deleted content (`pending_input_digest`, `tool_specs_digest`, `args_digest`) live only in `request_envelopes`/`derived_origins` rows of the deleted sessions, which are deleted. Readers' rows keep their own digests (of their own inputs). | Checked against migration 0006; no digest column of another session derives from the deleted text. |
| D12 | `DeletionPreview` reads, without locks or writes: deleted ids, dependents, row counts per table, readers to be fenced, transcript copies, parent checkpoints, journal rows still to project, and `Outside` copies it cannot remove: `backups/` files, the worktree, the workspace's files/Git history, provider requests. | Plan step 7; backups are listed, not claimed cleared. |

## 7. OPEN items and known limits

- **O-3:** approved 2026-10-26; §8.
- **Known limit:** while a reader of another connection holds an old snapshot, the deletion stays `cleanup_pending`
  and `DeleteSession` returns `ErrDeletionPending`; the WAL and the main file can still hold the content until the
  reader is gone and a later `DeleteSession`/`Open` truncates. Each attempt waits at most `migrate.CheckpointWait`
  (1 s). Desktop shows the error as a failed delete; a dedicated "cleanup pending" state is T7-S1.
- **Known limit:** `VACUUM` uses a temporary file (SQLite temp dir) holding the post-deletion database (no deleted
  rows), and needs free disk of about the database size.
- **Known limit:** content outside the database (workspace files, Git history, `backups/`, provider-side logs,
  OS-level copies such as Time Machine) is listed by `DeletionPreview`, not removed.
- **Cost:** per deletion, O(rows of the deleted sessions + transcript rows scanned + journal rows) in batches, plus
  one `VACUUM` and one WAL truncation.

## 9. P1 fix: a blocked WAL truncation was reported as a finished deletion

Reproduced at `9674321` (test `TestDeletionBlockedByAWALReaderIsNotReportedComplete` with a second SQLite connection
holding a read snapshot): `DeleteSession` returned `nil`, the privacy rows were already `cleaned`, the marker stayed,
and the sentinel was still in `lumencortex.db-wal`. Cause: `purgeDeletion` dropped `SettleCheckpoint`'s
`complete=false`, and `PurgeStep` set `cleaned` right after `VACUUM`, before the truncation.

Fix (`0262478` and `ada7138`; before the rebase `4e1e24b` and `cf4a5e7`): the truncation is the last step of the privacy row's cursor (D5);
`DeleteSession` returns `ErrDeletionPending`; the re-import refusal and tombstone of D10.

| Test | Real SQLite | What it proves |
|---|---|---|
| `TestDeletionBlockedByAWALReaderIsNotReportedComplete` | Engine + second connection holding a snapshot | blocked → `ErrDeletionPending`, rows `cleanup_pending`, marker kept, sentinel still at rest, retry still pending and bounded, re-import refused; reader gone → next delete finishes, no sentinel in main file or WAL, `cleaned`, marker gone; delete again `ErrNotFound`; re-import afterwards keeps the privacy row and is not withdrawn |
| `TestKilledBlockedDeletionIsFinishedOnceTheReaderIsGone/{open,delete}` | helper process deletes while the **parent process** holds the reader, gets `ErrDeletionPending`, is killed with SIGKILL | Open while the reader holds: still pending, bounded; reader gone → Open (`open`) or DeleteSession (`delete`) finishes; no sentinel; second Open has nothing pending; delete again `ErrNotFound`; other transcripts intact |
