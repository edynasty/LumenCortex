## 3. Tests

### 3.1 End to end (`TestRealEngineEndToEndProvenance`)

Real Engine and SQLite, git workspace, Auto effort with a bound judge model. Turn 1: `write_file a.txt` → shell `cat a.txt a.txt > b.txt` → `spawn_subagent` → `wait_subagent` → answer; turn 2 a plain question. Asserted afterwards:

- every envelope answered and lineage-complete; main envelopes per session = model requests received (parent 6, child 1); each main envelope's `tool_specs_digest` equals the digest recomputed from the tools that request actually carried;
- answered `auto_effort` envelopes = judge calls; each parent judge envelope shares its `run_id` with a main envelope whose `[first_seq, last_seq]` covers that turn's input row (see §6, S3 OPEN 1);
- `write_file` and shell executions completed, complete, under requests 1 and 2; `b.txt` on disk is `alpha\nalpha\n`; file edges are exactly `a.txt@<git blob> <- request 1` and `b.txt@<git blob> <- request 2`;
- child edge from request 3; wait result edge from the child session; transcript paired.

Mutation check: digesting all but the last sent tool fails the test at every request (then discarded).

### 3.2 Crash matrices on one fixture (`TestKilledAroundTheRequestAfterATool`)

The S2 matrix ran on a bare workspace with no prior tool; the S4 matrix crashes on the run's first tool call. The combination neither covers: a request crash in a session whose previous step already ran a side-effect tool. In the S4 fixture (git + test MCP server), step 1 completes a shell call appending to a counter; the child process is SIGKILLed at `after_admit`, `in_complete` and `before_answer` of request 2 (hooks fire on the second invocation). After reopen: envelope 1 answered/complete, envelope 2 `unknown`/`restart_no_answer`, the shell execution still `completed` under request 1 and untouched by Reconcile, no interrupted tool row, counter `x`. A resumed run sends exactly one request (3 envelopes, the first two unchanged), execution records unchanged, counter still `x`.

### 3.3 Cross-process (`runtime/crossprocess_unix_test.go`)

Helper processes re-execute the test binary (pattern of `runlock_process_unix_test.go`).

- **Workers and reader.** Two processes, each its own Engine, run 30 provider calls on different sessions at once; a third reads both sessions (`Session`, `TaskState`, transcript) and `ListSessions` continuously. Both runs complete; 31 answered main envelopes each; 20 completed, complete executions each (read_file is not admitted); reader errors 0 over ~400–550 reads; `PRAGMA integrity_check` = ok.
- **Busy.** While the worker's shell runs, the test process holds `BEGIN IMMEDIATE` **until the worker exits**. The worker's commit fails `database is locked`; its exit write fails too; the session stays `running`; the queued `write_file` never runs; one provider call. Reopen reconciles to `interrupted`/`stale_run_recovered`, the shell `outcome_unknown`, no envelope left `admitted`; the resumed run completes without re-running the shell (counter `x`). This is plan §3.1 rule 5 across processes.
- **Fence linearization.** Six trials, the fence committed by another process at a different point of a running worker each time, while a second worker runs 300 calls on another session. Every trial: answered envelopes and admitted executions were created before the fence; at most one envelope carries it (`failed/fenced` at request admission, or `unknown/fenced_before_answer` at the answer, admitted before the fence); with neither, the fence met a tool call, which then has no result row; provider calls = sent envelopes; at most one call began after the fence and only when the answer met it; the run ends `fenced`. The other worker completes with every envelope answered. Over the runs all three outcomes occurred (e.g. `{failed/fenced:1, tool call:2, unknown/fenced_before_answer:3}`).

Two test-design errors were found and fixed while writing these (no production change): a fixed 8 s hold was outlasted because a best-effort write spends the first 5 s busy wait before the commit starts its own (§5); and "no request begins after the fence" is too strong, since a request admitted before the fence may be sent after it (race mode made the gap visible) — the invariant is the accounting above.

### 3.4 Migration round trip (script)

`docs/reports/cognition/t1-s7-migration-roundtrip.sh <42ee234 worktree> <T1 worktree>` builds both `lcx-go` binaries, emits v1…v5 legacy workspaces (no binding) and runs, per version, two paths: **direct** (new binary opens vN → v6 and binds; old binary refuses with "schema is newer"; `db downgrade --to 5`; old binary lists the same sessions; new binary re-upgrades) and **old first** (old binary opens vN → 5, then the same sequence). Sessions are compared with the ids read from the fixture by `sqlite3`. All five versions pass both paths, exit 0; no database appears under `XDG_STATE_HOME` for legacy workspaces.

### 3.5 Whole-Engine write transactions (`TestRealEngineSideEffectStepTakesOneMoreWriteTransaction`)

Runs on fresh sessions of one Engine differ only in their last call. `[read, read, write_file]` and `[read, read, shell(true)]` each take exactly one committed transaction more than `[read, read, read]` (which repeats identically). Mutation check: shell skipping `AdmitExecution` fails it (then discarded). No CR: the counter is a `ConnectHook` on the registered driver, counting per database file (resolved symlinks), in test code only.

**Cause of the overrun.** A git-call log (wrapper on `PATH`) shows 5 git processes per run on `42ee234` and 15 on T1: about +3.3 per side-effect call (pre/post `hash-object`, `status`, `rev-parse`), at roughly 10 ms per process start on macOS. Read-only and memory steps are essentially unchanged, so the cost is the per-call pre/post snapshot that T1-S4's contract requires, not the transactions. Reducing it means sharing or caching snapshots across calls, which changes the per-call pre/post contract — a design decision for G1/the plan owner, not a T1-S7 change. In absolute terms it is ~31 ms per `write_file` and ~60–75 ms per shell call, against provider latencies of seconds. **Recorded as OPEN (§9); approval §7 calls a breach an anomaly requiring review, not a failure.**

## 5. Observation (pre-existing, not changed)

`runtime/agent.go` journals every loop event synchronously on the run goroutine and discards the error (`_ = e.store.Journal(...)`, identical at `42ee234:runtime/agent.go:368`). Under writer contention one event costs up to the 5 s busy timeout before the next real write starts its own wait; the busy test's run spent ~17 s (swallowed journal write, failed commit, failed exit write). Correctness is unaffected (the journal is observability; the commit still fails closed). Recorded in the workspace backlog as P3; not changed in T1.
