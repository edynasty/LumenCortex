## 3. What changed

### 3.1 `Store.Journal` — a whitelist, not a blacklist

Every journal payload is marshalled, decoded (with `json.Number`, so numbers keep their exact text), projected,
and written. The projection keeps:

- **any number or boolean** — counts, byte sizes, sequence numbers, exit codes, durations. A number cannot carry
  a body, so it needs no name;
- **a string only under a named field and only when ≤ 128 bytes** — the event type (`type`, `eventType`,
  `event`), identifiers and sequence labels (`sessionId`, `parentSessionId`, `childSessionId`, `id`, `ids`,
  `seq`, `nextStep`, `taskId`, `toolCallId`, `callId`, `relationId`, `check`, `modelRef`, `nextModelRef`,
  `provider`, `model`, `agent`), the tool name (`name`, `tool`, `toolName`), a status or exit-code word
  (`status`, `phase`, `class`, `kind`, `stream`, `origin`, `role`, `ok`, `denied`, `cancelled`), and a time
  (`at`, `time`, `timestamp`, `startedAt`, `endedAt`);
- **arrays of those** under a named field (`ids`).

Everything else is dropped, including a field a later change adds to an event: a field is private until it is
named. The one object the projection enters is `data` — the agent loop journals an event as
`{"sessionId": …, "data": <event data>}` and the event data is projected by the same rule. No other object is
entered, so a tool's `args` cannot smuggle a whitelisted key name through to its value. A payload that is not an
object, or that keeps nothing, becomes `{}` (the column's `json_valid` CHECK still holds).

Consequence: `tool.output` chunks, tool arguments, goals, final answers, shell commands and failure texts are no
longer written to `journal` at all. Old rows are untouched (T3 owns the cleanup).

### 3.2 Parent child-session checkpoints

`subagent.spawn` keeps `childSessionId`, `status: "created"` (the child's status when the checkpoint is written;
`Start` follows) and `agent`. `subagent.stopped` keeps `childSessionId`, `status` and `agent`. The goal and the
child's final answer are gone from both; `subagent.start_failed` keeps `childSessionId`, `status:
"interrupted"`, `agent` instead of the error text (that text is already the child's `error_json` column).

The in-memory events are unchanged: `subagent.spawned` still publishes the goal, and `subagent.stopped` still
publishes the child's final text and, on failure, the error — the checkpoint and the event are now built as two
maps instead of sharing one.

### 3.3 `RunShell`

The `tool.shell` journal row carries `sessionId`, `name`, `exitCode`, `stdoutBytes`, `stderrBytes`,
`cancelled`; the command line is not written. The `tool.end` event payload is byte-for-byte what it was, so the
Desktop keeps the command and the error.

## 10. OPEN items and known limits

- **OPEN (T3):** rows written before this slice keep their bodies. Nothing rewrites or scrubs them.
- **OPEN:** `agent_steps.json` records each tool call's `Args` (`internal/agent/loop.go`, `record.ToolCalls`), and
  `task_states` holds Task State bodies. Both are body copies outside this slice's files; they are not journal or
  parent-checkpoint copies and were not touched.
- **OPEN:** the `subagent.start_failed` checkpoint no longer carries the failure text (only the child's
  `error_json` column and the child session row do). If a host needs the reason on the parent's checkpoint, that
  is a contract decision, not a silent omission.
- **Known limit:** a journal string is kept only under a named field and only up to 128 bytes. A legitimately
  long identifier (a very long tool name, an exotic session id) would be dropped rather than truncated; today the
  longest such value is a 30-character RFC 3339 timestamp.
- **Known limit:** `llm.request`'s `tools` array (tool names) and `reasoningEffort` are dropped: they are arrays
  of names and an enum the whitelist does not name. Add them to `journalPayloadStrings` if the audit needs them.
- **Known limit:** the raw byte scan is best-effort for a WAL file (a row can straddle a frame boundary); the SQL
  scan is authoritative, and the vacuumed-copy scan is the byte-level proof.
- The Desktop reads checkpoints (`GetSessionCheckpoints`) but no in-repo Desktop code parses the checkpoint JSON
  payload; dropping `goal`/`final` from the parent checkpoint changes no in-repo renderer. [INFERENCE: an
  out-of-repo client that parses those fields would lose them; the plan requires their removal.]
