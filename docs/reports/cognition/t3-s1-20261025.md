## 2. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | The unit of revocation is a **session**. `RevokeSource(kind, …)` accepts `session` only; any other kind is `ErrUnsupportedSource`. | DATA §5 step 1 names Session revocation; a file is workspace content (its edges already go stale by blob), a request/message/check belongs to a session. Finer units are not needed for R1a and would need ref-level fences at admission (no longer O(1)). |
| D2 | The reverse walk uses `derived_origins(source_kind='session', source_ref)`, `session_relations` children and `child_session` edges. Envelope `refs_json` is **not** walked. | Envelope refs are session-local (`ts:…`, `sys:…` digests, `internal/agent/envelope.go:84-119`): they never name another session, so the session itself — always fenced — covers them. |
| D3 | Each reached session gets its own `session` fence row with the revocation's epoch; the source's row carries the report as `tombstone_json` (ids and counts only), the others a pointer. The epoch is the report's handle. | Admission stays the existing O(1) `sessionFence` read (plan §3.4); no new table or column. |
| D4 | Bound: `MaxRevokeSessions = 256`; past it **every session of the database** (= the project: one database per workspace, `runtime/statedir.go`) is fenced and `expanded=true`. | DATA §2/§5: past the bound, widen conservatively. |
| D5 | `sourceFenced` treats a `session` source as fenced when that session has a fence. | Without it an edge read before the revocation and committed after — or citing a session reached transitively — was not refused (the only fence rows written are `session` rows). |
| D6 | Late commits keep the S1 fail-closed branch: the body is not stored, the envelope ends `unknown/fenced_before_answer`, the run ends `fenced`. | DATA §5 allows ("可") storing a late answer for an ordinary revocation; not storing is the stricter option and needs no new state. |
| D7 | `read_thread` and `recall` results store `message` edges from the tool row to every session they carry (the read thread and its non-withdrawn children; every recall hit), as of each session's newest seq. | **Gap found:** since T2-S1 these tool rows carried another session's text with no edge, so a revocation could not find a reader and a late read was not refused. This is required for the T3-S1 acceptance, not new scope. |
| D8 | A check does not run in a fenced session (`runChecks.Decide` → `session.ErrFenced` → run exits `fenced`). | DATA §5 "check 自动执行仍先校验…scope deny". It is a read before running, not an admission row (T4-S2 owns the check episode). |
| D9 | In-process cancellation: the Engine tracks each executing loop (`preparedRun.execute`), `RevokeSource` cancels the fenced ones after the commit and waits until each loop has returned. | Plan step 4. Other processes are not signalled (no IPC — a stop condition); they stop at their next admission or commit. |

## 7. OPEN items and known limits

- **OPEN (T3-S3, verified by a throwaway probe, then deleted):** revoking a child task leaves its parent
  unfenced (the parent cites the child only after a delivery). The parent's next `Start` then fails with
  `session or source is fenced` and writes nothing, because the pending `OriginTaskResult` delivery's edge cites the
  fenced child. This is fail-closed (no content flows), but the parent cannot run until T3-S3 makes the delivery
  withhold or annotate a fenced child's result — `OriginTaskResult` is in T3-S3's lane.
- **Known limit (D8):** a check already running when the revocation commits may store its result after it. A check
  sends nothing to a provider; T4-S2's closed episode is where a check start becomes an ordered record.
- **Known limit (D9):** a run in another process is not cancelled; it stops at its next admission or commit, and
  what it admitted before is in the report (`InFlightNow` may show `admitted` until that process settles it).
- **Known limit:** an edge stored before T3-S1 does not exist for reads made by `read_thread`/`recall` before this
  commit; such a reader is not reached by a revocation. Development databases only (no release carries T2-S1).
- **Cost:** one revocation = one write transaction with ≤256 indexed walk queries and one exposure query per reached
  session; admission unchanged (one indexed read); each `read_thread`/`recall` result adds ≤29 edge rows and one
  `NewestMessageSeq` read per carried session. Not benchmarked.
