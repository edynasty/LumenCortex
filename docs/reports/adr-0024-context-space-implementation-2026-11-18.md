## 3. 工作区重检机制的真实职责边界声明（`R2-03` 诚实澄清）

为彻底消除前版报告将提示词通知表述为“强制重检/强制拦截”的歧义，现按真实生产代码严格区分三层机制的精确作用范围：

1. **Prompt Notice（提示词级显式告知，非运行时拦截器）：**
   - 当触发 Stage R1（`appendFloorRelaxationNotice`）或 Stage R2/R3（`appendPinnedGateAndRelaxationNotice`）时，系统在当步 `State` 消息中注入 `[Context Window Notice — Floor Relaxation]`（Stage R2/R3 同时注入 `[Pinned Completion-Gate State]` 与近期因果变更摘要），明确告知模型哪些历史序列区间已被省略，并指示模型在修改代码或提议完成前先用 `read_file`、`search_text` 或 `git status`/`git diff` 重新检查工作区。
   - **边界：** 该文本属于面向模型的上下文告知，**Runtime 不会在 `Loop` 或 `toolset` 入口拦截未先调用只读工具的模型工具调用**。
2. **文件编辑工具 CAS 保护（仅覆盖 `editing.Engine` 管辖的编辑工具）：**
   - `write_file`、`replace_in_file`、`edit_lines` 与 `apply_patch` 由 `internal/editing/engine.go` 与 `internal/toolset/editing.go` 的读集版本/哈希 CAS 及原子不覆盖创建机制保护（拒绝陈旧覆盖或并发已存在路径创建）。
   - **边界：** **`bash` 子进程命令与 `mcp:*` 外部工具不经过 `editing.Engine` CAS**；若模型忽略提示词直接执行写盘 `bash` 命令或可变 MCP 工具，Runtime 不会做前置拒绝（但其副作用会被 `executionTierOf -> tierWorkspace` 记为 `MutationUnknown`）。
3. **Completion Gate 最终完成复核（拦截错误完成声明）：**
   - 模型在宣称任务完成时仍必须通过宿主的 Completion Gate / Verification 检查；未消除的失败测试或后台运行作业会再次产生 `OriginCompletionBlocked` 拒绝完成。
4. **治理跟踪状态：** 是否在未来引入运行时级工具前置硬守卫（以及如何避免误伤合法的 `go test` / `git status` 类 `bash` 诊断命令）按 Owner 决策作为独立架构增强项保留在台账中，状态为 **`OPEN (P3)`（`R2-03`）**。

  1. **哪些项目在部分失败后尝试自动恢复（automatic restoration）？** 上述 6 个项目中，**没有任何一个**对“已向目标路径发布的既有普通文件”执行多文件事后原地覆写/截断恢复；Git 仅在全部 `.lock` 阶段未提交前通过删除私有 `.lock` 临时文件放弃事务。
  2. **哪些项目选择保留部分状态并返回错误？** **OpenCode**（`patch.ts` 显式返回 `Completed before failure: ...`）与 **OMP**（`edit/index.ts` 返回 `isError: true` 并保留已执行的文件改动）均在多文件批次中途失败时保留实际磁盘状态并向 Agent 报告错误；`tempfile` / `renameio` / **Pi** 则将原语限定在单文件作用域。
  3. **这些方案实际提供什么安全保证？** `tempfile::persist_noclobber` 提供内核级**不覆盖创建**（`RENAME_NOREPLACE` / `link` / `MoveFileExW(0)`）；`renameio` 与 Git `lockfile` 提供读者不会读到半写文件的**命名空间原子替换**（读者要么看到旧 inode 要么看到新 inode），且 Git `.lock` 额外为**遵守 `.lock` 协议的合作进程**提供互斥。
  4. **它们能否防御非合作并发写入者（uncooperative concurrent writers）？** **不能。** 覆盖式 `rename(tmp, dst)` 会直接替换目录项并丢弃非合作进程向旧 inode 追加的 `O_APPEND` 数据；而原地 `Write + Truncate` 也不具备内核级基于内容的原子 CAS 原语。

### 9.2 R5 强制反向自检十三问（Self-Criticism）

1. **`Close()` 失败的既有文件是否仍可能触发破坏性回滚？** 不会。`Engine.write` 仅将 `p.published && p.created` 的新建文件纳入故障文件自身回滚；既有文件（`!p.created`）的 `Close()` 失败绝不进入 `e.rollback`，仅执行只读 `inspectExternalModificationReadOnly` 检查并原样保留磁盘内容（`TestR5RollbackSafetyAndStateIntegrity` 场景 3 与真实独立 OS 子进程场景 8a 实证）。
2. **多文件回滚前是否仍可能覆盖外部修改？** 在校验时刻已存在的全部外部修改（外部追加、外部原子替换含等长/同字节、同 inode 等长原地修改、外部删除、已删文件被外部重建）均会被 `verifyUnmodifiedForRollback` / `removeCreatedAtRollback` / `restoreDeletedAtRollback` 拦截并原样保留，记为 `PublishExternalModification`；但诚实披露：**POSIX 与 Windows 均不提供针对非合作外部写入者的原子 compare-and-swap 原地覆写原语**，校验与 `f.Write` 之间存在极窄的 OS check-then-write TOCTOU 窗口（写入后、关闭前落地的并发写会被回读检出并记为 `PublishExternalModification`），该残余窗口归属既有 `PRE-02`（`OPEN P2`）。

### 9.3 R6 强制反向对抗自检十五问（§12 Self-Criticism and Adversarial Verification）

1. **我是否只是把竞争窗口挪到了别处（Did I merely move the race window）？** 对等长与增长型恢复（`len(original) >= len(next)`，包括 `R5-01` 原复现场景），`f.Truncate` 被**彻底移除而非移动**，因此 `Write -> Truncate` 截断外部追加的竞争窗口完全消失。对收缩型恢复（`len(original) < len(next)`），在调用 `f.Truncate` 前新增了 `verifyPreShrinkForRollback`（核验描述符与路径身份、精确长度与完整字节），任何此前已落地的外部追加都会直接中止截断并保留磁盘数据；至于 `verifyUnmodifiedForRollback` 与 `write(2)` 之间、`verifyPreShrinkForRollback` 与 `ftruncate(2)` 之间的亚微秒级内核间隙，由于 POSIX/Windows 无内容 CAS 写/截断原语，无法在非合作进程模型下凭用户态消除，已诚实保留在既有 `PRE-02`，绝不声称已消除。
2. **并发写入者是否仍可能丢失字节（Can a concurrent writer still lose bytes）？** 在校验前、校验后追加（当 `len(original) <= len(next)` 时）、`Write -> Truncate` 之间（全部长度关系）、`Readback -> Close` 之间以及 `Close` 之后的外部 `O_APPEND` 与原子 `rename` 替换，外部字节均 **100% 保留**（经 `TestIndependentR5AppendAfterRestoreWrite` 4 子项与 `TestR6RollbackRaceAndFaultMatrix` 实证）。唯一残余可能丢失外部字节的情形是非合作进程恰好在校验完成后、`write(2)`（当原地非追加覆写或 `len(original) > len(next)`）或 `ftruncate(2)`（当 `len(original) < len(next)`）进入内核前的极窄窗口内写入同一 inode，该情形属于公开记录的既有 `PRE-02`（`OPEN P2`）。
3. **我是否新增了任何新的破坏性恢复步骤（Did I add a new destructive recovery step）？** 没有。相反，R6 移除了不必要的 `f.Truncate`，在收缩前增加了拒绝截断守卫，并将 `restoreDeletedAtRollback` 从直接原地创建改为同目录私有临时文件 + `publishTempNoReplace` 原子不覆盖发布（中途 `EFBIG` 仅清理私有临时文件，绝不在目标路径留下半写残骸或覆盖外部新建文件）。
4. **状态不确定的文件是否可能被报告为“已完全回滚”（Can an uncertain file be reported as fully rolled back）？** 不会。`writeRestoreConditional` 必须在 `verifyDescriptorAfterRestore`（`Close` 前）与 `verifyPostRestoreDisk`（`Close` 后只读重开核验路径身份、长度与全部字节）全部通过且 `f.Close() == nil` 时才返回 `PublishRolledBack`；`04_append_after_readback_before_close`、`05b_replacement_between_validation_and_restore`、`09a_rollback_close_failure` 与 `09b_rollback_readback_descriptor_failure` 实证任何异常均返回 `PublishExternalModification` 或 `PublishRollbackFailed`，且事务级 `CommitState` 为 `partially_published`（绝非 `rolled_back`）。
5. **回执（`CommitReceipt`）是否可能声称与磁盘实际不符的内容（Can the receipt claim content that differs from disk）？** 不会。`PublishSucceededWithPostError`、`PublishRollbackFailed`、`PublishExternalModification`、`PublishUncertain` 以及失败事务中全部未验证的 `PublishNone` 文件（如因外部并发修改触发 CAS 冲突的 `e.txt`）统一置 `Verified = false`、`NewSHA256 = ""`、`NewRev = ""`（`10_multifile_mixed_outcomes_and_unverified_conflict_sha` 实证；仅仍存在 `verifyPostRestoreDisk` 返回之后的自然并发写入时间演进）。
6. **回滚失败是否可能被原始错误掩盖而丢失（Can a rollback failure be lost behind the original error）？** 不会。`Engine.write` 通过 `errors.Join` 合并主错误与全部 `e.rollback` 错误；`toolset.formatCommitFailurePayload` 对完整 `err.Error()` 脱敏输出并在 `files[].error` 保留单文件回滚错误摘要。
7. **`SnapshotStore` 是否可能残留无效修订（Can SnapshotStore contain an invalid revision）？** 不会。失败提交分支对 `PublishSucceededWithPostError`、`PublishRollbackFailed`、`PublishExternalModification`、`PublishUncertain` 及已回滚新建文件一律调用 `e.snaps.ForgetPath(plan.Actor.Session, p.key)`，严禁调用 `e.register`。
8. **`MutationUnknown` 是否可能退化为 `MutationNone`（Can MutationUnknown become MutationNone）？** 不会。任何脏失败或部分回滚均置 `DirtyFailure = true`，`postExecution` 与 `sealFilesMutation` 强制记录 `OutcomeUnknown` 与 `;cm=unknown`，在线与冷 SQLite `Resume` 均严格恢复为 `MutationUnknown`（`TestR6PartialRollbackAndDiagnosticsColdResume` 实证）。
9. **Agent 是否可能收到格式损坏的非法 JSON（Can the Agent receive malformed JSON）？** 不会。`appendNestedPartialPublication`、`preserveErrorToolContent` 与 `formatCommitFailurePayload` 对结构化结果全程通过 `encoding/json` 序列化，彻底移除了向 JSON 末尾拼接纯文本的逻辑，且禁止对原始 JSON 字节流做切片截断。
10. **JSON 截断是否可能删除必需的血缘字段（Can JSON truncation delete a required provenance field）？** 不会。`compactJSONObjectToBudget` 将 `protectedToolResultKeys`（含 `sourceSessions`、`applicationId`、`adoptionId`、`sessionId`、`id`、`withdrawn`、`session`、`node`、`messages`、`children`、`evidence`、`hits`、`sources`、`maintenanceSessionId`、`candidates` 等全部 `resultSessions` 依赖键）列为不可删除集合，仅裁剪 `results`/`stdout`/`pad` 等非血缘大字段；`apply_experience` `8500B` 超限实测 `derived_origins` 消息来源边与 `RevokeSession` 级联 100% 保留。
11. **宿主机绝对路径是否仍可能泄露进 SQLite（Can absolute host paths still leak into SQLite）？** 对**新产生**的结构化工具结果、编译/类型检查诊断（含同包兄弟 `.go` 文件与 `unknown_rev`）及常规错误文本（POSIX、含空格工作区、符号链接、Windows 盘符、UNC），均经 `relativizeDiagnosticPath`、`sanitizeStructuredPath` 与 `sanitizeErrorText` 净化后才写入 `session_messages`（`TestR6PartialRollbackAndDiagnosticsColdResume` 冷重开 SQLite 实证零泄露）。诚实边界：历史已落库的旧 SQLite 行未做迁移清洗，且类似 `bash`/`eval` 自由文本标准输出按设计原样返回其命令输出。
12. **工作区兄弟路径是否仍可能被错误改写（Can sibling paths be accidentally rewritten）？** 不会。`sanitizeErrorText` 与 `sanitizeEngineError` 彻底废除了无边界 `strings.ReplaceAll`，严格校验右词法边界与路径组件分隔符：`<workspace>-sibling/secret.txt`（含带空格工作区、`C:\...\Repo-sibling\...` 与 `\\srv\share\ws-sibling\...`）均准确净化为 `<outside-workspace>/secret.txt`，绝不会再产生 `.-sibling/secret.txt`。
13. **我是否制造了不必要的抽象（Did I create unnecessary abstractions）？** 没有。未新增任何包、接口、表或后台组件，全部修复均在既有 `internal/editing`、`internal/toolset` 与 `internal/agent/execution.go` 原位函数内以百余行纯函数完成。
14. **成熟开源实现是否本可以用更简单的方式解决（Could a mature implementation have solved the problem more simply）？** §7.5.3 对照表明：OpenCode 与 OMP 通过“完全不做多文件自动回滚、直接保留部分落地状态并报错”实现最简安全，而 LC 基线契约要求无外部冲突时支持多文件回滚；因此 LC 在无冲突路径采用“等长/增长零 `Truncate` + 收缩前核验”最小修正，并在检测到任何外部冲突/不确定时立即采用与 OpenCode 一致的保守部分提交策略（方案 B），兼顾了基线兼容性与外部数据零破坏原则。
15. **文档声称的保证是否强于底层文件系统原语实际提供的能力（Are claimed guarantees stronger than the actual filesystem primitives）？** 绝不。本报告与双语 `ADR-0024` 明确区分了内核级原子不覆盖创建（`link`/`RENAME_NOREPLACE`/`RENAME_EXCL`/`MoveFileExW(0)`）与非原子的既有文件条件恢复，明确声明不提供 `fsync` 掉电持久性、不声称解决 `PRE-02` 亚微秒级非合作并发写 TOCTOU，并将未经原生 Windows 主机实测的 `R5-06` 明确保留为 `UNVERIFIED — Potential P2`。
