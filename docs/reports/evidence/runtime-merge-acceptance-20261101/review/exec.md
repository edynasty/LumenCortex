## Unverified / not findings

- **U1 — pgid reuse after Wait (MCP).** In `Client.Close` (`client.go:373-375`), `KillGroup` runs after `cmd.Wait` has reaped the server. And when the grace expires, `readLoop`'s deferred `killGroup` (`:417`) also runs after `Wait`: `Wait` closes the stdout pipe, and only then does `readLoop` return. Both send `SIGKILL` to `-pid` after the pid has been freed. It only hits something else if, within microseconds, the pid is reused by a new process that makes itself a group leader. Not reproducible, so not a finding. Removing the post-`Wait` `KillGroup` loses nothing (the group was already killed by `readLoop`/`cmd.Cancel` while the server was a zombie). The bash runner kills after `Wait` the same way, and that predates this branch.
- **U1b — double Wait.** None found: only `Close` calls `cmd.Wait`, inside `closeOnce`; the `Start` error paths go through `Close`.
- **U2 — Playwright's Chromium may be outside the server's group.** [INFERENCE, not run: no network/Playwright] Playwright appears to launch browsers with `detached: true` (setsid) on POSIX. If so, `KillGroup` does not reach Chromium; only the 2 s grace (the server closing its own browser) does, and a server that takes longer than 2 s is SIGKILLed with the browser left behind. The repository tests use a `sleep` child in the same group, so they do not cover this.
- **U3 — MCP `Close` can hang on stderr.** `cmd.Wait` has no `WaitDelay`, and stderr is a Go writer. A server child outside the group that holds stderr would block `Close` indefinitely. This predates the branch (`cog/r1a` `Close` had the same `Wait`); 15f9039 makes it less likely.
- **U4 — recovery leaves the dead owner's job running.** Recovery marks the dead owner's job `outcome_unknown` but leaves its process group running (`restart_unix_test.go` kills it by hand). ADR-0019 does not ask for a kill; this is a design question for the Owner.
- **U5 — Windows liveness.** `processAlive` is always false on Windows. A second Engine on the same database marks the first one's running jobs `outcome_unknown` and adopts its queued jobs while the first is still running them. This is documented in `process_windows.go`; not run on Windows.
- **U6 — `pending` map leaks.** Small leaks: an entry stays when a job finishes between `Cancel`'s `GetJob` and `cancelRunning`, or when `newJobOutput` fails (`jobs.go:704-707`, before the cleanup defer is registered).
- **U7 — byte-sliced commands.** `jobgate.go:49` cuts commands at byte 57, which can split a UTF-8 rune; `runtime/jobs.go` uses `truncateUTF8`. JSON encoding turns the broken rune into U+FFFD, so nothing breaks.

## Checked and found correct (evidence: code read + existing tests above)

- **Claim CAS:** one guarded UPDATE per transition; `TestCASRaceMovesAJobOnce` races 8 claimers against 8 cancellers.
- **Cancel during claim:** the `pending` map is read under the same lock that registers `active`, and the kill is sent right after start.
- **Recovery:** running → `outcome_unknown`, never re-run; queued jobs adopted (`TestRestartAfterOwnerDeath`).
- **Queue/run limits:** counted inside the insert transaction.
- **`Engine.Close` order:** scheduler → plugins → bus → LSP → MCP → jobs → store → diagnostics. `jobs.Close` records terminal states while the store is still open; `job.state` events during Close are dropped by the closed bus, but the journal row is written.
- **`lcx-go` signals:** `SIGINT`/`SIGTERM` → `NotifyContext` → deferred `engine.Close`, so `Setpgid`'d jobs and MCP servers are not orphaned by Ctrl-C.
- **Deadline:** monotonic anchor; tool deadline = deadline − margin; the `exit` mapping turns cancelled/storage/provider exits into `KindDeadline` via `context.Cause`; children inherit the tool deadline; `job_wait` and the foreground timeout are bounded by it; a call past the deadline is not started.
- **Budget:** admitted before every attempt, failover included; tool calls past the allowance are neither stored nor run; spend reported on every exit, panic included.
- **Completion gate:** at most 2 refusals, a lookup error does not block, and `endRunJobs` runs after every `loop.Run` (single call site, `runtime/agent.go:138-139`).

**RT-exec-10 deferral: accepted.** The implementer's objection to my suggested fix is correct. A shell that traps TERM exits 0 after a real timeout signal: `bash -c 'trap "exit 0" TERM; sleep 30 & wait'` killed with SIGTERM after 1 s printed `exit=0`. The error is conservative: interrupted/`outcome_unknown` is reported, and the child group is killed, which the runner does on shell exit anyway. Deferring it is proportionate.
