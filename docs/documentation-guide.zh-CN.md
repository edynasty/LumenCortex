# 文档编写和维护规范

本文规定 LumenCortex 文档应该怎么写，避免 README 变成设计堆积、实现状态写错，或同一功能在不同文件中说法不一致。

## 文档分层

1. **README**：介绍项目、主要能力、安装运行方法和文档入口。
2. **系统文档**：说明整体架构、组件关系和执行流程。
3. **组件文档**：说明某个 API、功能和具体约束。
4. **验证文档**：说明哪些行为真正经过测试或运行。
5. **ADR**：记录重要架构决定及原因，避免反复争论。

## 一个问题只保留一个权威说明

| 问题 | 主要文档 |
|---|---|
| 系统是什么 | system-overview |
| 整体架构 | architecture |
| Attention 如何检索和选择上下文 | attention-light-algorithm |
| 一次 Run 如何执行 | execution-flow |
| Workflow 如何约束任务 | workflow-contract |
| 数据如何保存 | data-model |
| 安全边界是什么 | security-and-trust |
| 哪些能力经过验证 | validation |
| 还有哪些限制 | standalone-readiness |

其他文档应该链接到权威说明，不要复制整段内容。

## 状态用词

- **已实现**：源码中有对应实现。
- **已验证**：测试或运行证据覆盖相同路径。
- **部分实现**：仍缺少重要功能。
- **计划中**：只有设计，没有完整实现。
- **证据不足**：有代码，但缺少要求的运行证明。

不要使用“完全安全”“生产就绪”“完全替代”“完整对齐”等没有边界的说法。

## 写作要求

- 用普通语言说明功能解决什么问题。
- 给出真实代码位置和适用边界。
- 重要状态变化用表格或示例说明。
- 说明限制和失败行为。
- 设计目标必须标注为目标，不能写成已实现。
- README 只保留用户需要的信息，详细机制放到组件文档。
- 中文文档应由中文读者直接阅读，不要逐句保留英文句式。
- 技术名词、API、字段和命令保持原样，首次出现时解释含义。

## 修改完成标准

涉及行为的代码修改，通常还要同步更新权威文档、验证证据和已知限制。架构变化需要更新图和 ADR。新增文档应有中英文入口；不要求逐字翻译代码标识和命令。
