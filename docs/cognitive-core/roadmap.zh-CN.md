# Cognitive Core 后续工作

这份路线沿用 Astra 原来的 P0～P3 顺序，并结合 Fable 对 Go 实现的审查。它不是要求马上增加新模块。

## P0：先保证知识可靠

目标：让系统知道每条知识适用于哪里、何时有效、依据是什么。

- 统一项目/环境范围、时间、证据和来源。
- 明确知识和经验的状态变化。
- 每次读取时检查是否仍然有效。
- 区分原始来源、共享经验和每个使用者自己的记录。
- 确保修订、撤销和恢复在事务中完成。
- Go 是唯一权威实现。

本候选已补齐统一 Scope/Time/Evidence、CAS/依赖、生命周期和读者隐私调用链，尚未合并；精确工程与独立审查状态见交付报告。

## P1：让过去的经历帮助未来任务

目标：把具体任务经历整理成有条件、可验证的经验。

- 区分观察、解释、假设和操作方法。
- 从真实任务结果中提取经验候选。
- 写清使用前提、处理方法、预期结果和不适用情况。
- 使用真实检查和反例验证。
- 当前任务满足前提时才允许复用。
- 分开记录每个使用者的采纳和结果。
- 根据反馈修订、缩小范围、失效或删除。

普通 Agent 已连接“提案 → 任务结束提取/验证 → 独立采纳/应用 → 反馈/修订”。原操作序列的条件复用是明确权限边界；任意参数迁移与长期任务收益仍需真实需求/证据，不能从工程完成推导。

## P2：让系统知道自己不知道什么

目标：根据证据决定行动，而不是强行给结论。

- 明确记录未知、冲突和证据缺口。
- 能在执行、补充检查、提问、暂缓和停止之间作选择。
- 记录判断依赖的假设。
- 发现经验不适用于当前任务时停止套用。
- 支持证据变化后的重新判断。
- 模型提出建议，Framework 掌握验证和状态修改权限。

`assess_cognition` 已记录带确切版本和证据的判断；冲突和未解决前提不能静默成为事实。模型负责假设与补证/提问/暂缓/停止，Framework 不代替通用推理，也不证明因果关系。

## P3：历史变多后仍然好用

目标：控制检索成本和长期记忆规模。

- 提高任务相关信息的检索质量。
- 整理经历摘要和长期知识。
- 分开统计最近使用、使用频率和实际价值。
- 按证据管理保留、归档和容量。
- 优化大规模图和经验查询。
- 只有确有需要时才考虑物理冷热分层。

本候选已实现重要信息保护、所有者活跃容量维护、等价证据归并、读者私有访问统计和独立结果统计。物理冷热分层、大型选择域查询优化、因果收益估计必须以实测需求为依据；当前不新建记忆管理器或主观认知评分项目。

## 不要做的事

- 不要为了架构图好看就增加 GraphRAG、GNN、ANN 或新数据库。
- 优先补齐现有 Go 机制之间的关系。
- Node.js 研究只作历史参考，不作为生产实现。
- 不要把设计目标写成已经实现。
- 测试通过不等于证明系统长期变聪明。
