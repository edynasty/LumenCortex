# Cognitive Core 后续工作

这份路线沿用 Astra 原来的 P0～P3 顺序，并结合 Fable 对 Go 实现的审查。它不是要求马上增加新模块。

## P0：先保证知识可靠

目标：让系统知道每条知识适用于哪里、何时有效、依据是什么。

- 统一项目/环境范围、时间、证据和来源。
- 明确知识和经验的状态变化。
- 每次读取时检查是否仍然有效。
- 区分原始来源、共享经验和每个使用者自己的记录。
- 确保修订、撤销和恢复在事务中完成。
- Go 是唯一权威实现。

扩展 P0 已在独立候选中实施和审查；未合并前不能算作 main 已有能力。

## P1：让过去的经历帮助未来任务

目标：把具体任务经历整理成有条件、可验证的经验。

- 区分观察、解释、假设和操作方法。
- 从真实任务结果中提取经验候选。
- 写清使用前提、处理方法、预期结果和不适用情况。
- 使用真实检查和反例验证。
- 当前任务满足前提时才允许复用。
- 分开记录每个使用者的采纳和结果。
- 根据反馈修订、缩小范围、失效或删除。

主要缺口：如何从一次具体经历中提炼可迁移的方法，同时不丢失适用条件。

## P2：让系统知道自己不知道什么

目标：根据证据决定行动，而不是强行给结论。

- 明确记录未知、冲突和证据缺口。
- 能在执行、补充检查、提问、暂缓和停止之间作选择。
- 记录判断依赖的假设。
- 发现经验不适用于当前任务时停止套用。
- 支持证据变化后的重新判断。
- 模型提出建议，Framework 掌握验证和状态修改权限。

元认知是贯穿现有领域的职责，不必另建一个 Agent 或服务。

## P3：历史变多后仍然好用

目标：控制检索成本和长期记忆规模。

- 提高任务相关信息的检索质量。
- 整理经历摘要和长期知识。
- 分开统计最近使用、使用频率和实际价值。
- 按证据管理保留、归档和容量。
- 优化大规模图和经验查询。
- 只有确有需要时才考虑物理冷热分层。

## 不要做的事

- 不要为了架构图好看就增加 GraphRAG、GNN、ANN 或新数据库。
- 优先补齐现有 Go 机制之间的关系。
- Node.js 研究只作历史参考，不作为生产实现。
- 不要把设计目标写成已经实现。
- 测试通过不等于证明系统长期变聪明。
